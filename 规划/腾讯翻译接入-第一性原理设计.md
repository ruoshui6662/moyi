# 腾讯翻译（TMT）接入 — 第一性原理设计

> 目标：在现有「OpenAI 兼容 LLM + DeepL 传统 MT」双后端之上，新增腾讯云机器翻译（TMT）
> 作为第二个**传统 MT 后端**。API 由用户在腾讯云控制台手动申请（SecretId / SecretKey），
> 在插件设置页填写后使用。
>
> 调研对象：腾讯云官方文档（document/api/551）与官方 Node SDK（`tencentcloud-sdk-nodejs-tmt`）。

---

## 一、第一性原理：腾讯翻译在项目里扮演什么角色

插件解决的问题只有 6 件事（见 `浏览器翻译插件-第一性原理与自研路线.md`），
腾讯翻译只影响其中第 3 件「把原文送到 AI」的一个子集——**替换"什么角色在翻译原文"**。

```
网页 DOM → 找文本 → 切段落 → 【调谁翻译（唯一变化点）】 → 写回 DOM → 撤销/重翻
```

拆开看，现有代码里「调谁翻译」的角色只有两类：

| 角色 | 代表 | 特征 |
|---|---|---|
| LLM 提示词型 | OpenAI 兼容 5+1 家 | 有模型、有提示词、可流式、可批量打标签、按 token 计费 |
| 传统 MT API 型 | DeepL | 无模型、无提示词、无流式、整批按序返回数组、按字符计费 |

**腾讯翻译与 DeepL 是同一角色**（传统 MT API）：无模型 / 无提示词 / 无流式 / 按字符计费。
所以接入腾讯翻译的第一性原理结论是：

> **不要为腾讯翻译复制 DeepL 的分支，而是把「传统 MT API 型」抽象成一个适配器家族，
> DeepL 与腾讯翻译各实现一个适配器。** 当前 `kind === 'deepl'` 的分支散布在
> `trans.ts` / `background.ts` / `options/main.ts` 共 4-5 处，每加一家 MT 就多一份分支，
> 是不可扩展的；先把家族抽象立起来，再让腾讯翻译作为第二个成员落地。

## 三、架构设计

### 3.1 后端家族抽象：`kind` 收敛为两值

现状：`kind: 'openai' | 'deepl'`，每处判断都写 `=== 'deepl'`。
变更：`kind: 'openai' | 'mt'`，DeepL 与腾讯翻译的 `kind` 都是 `'mt'`；
「具体用哪家 MT」由 provider 元数据与适配器注册表决定。

```
providers.ts  kind: 'openai' | 'mt'
      │
      ▼
service/mt.ts（新）：MT 适配器注册表 + 统一接口
      ├── deepl.ts    实现 MtAdapter（存量，kind 字段从 'deepl' 改为 'mt'）
      └── tencent.ts  实现 MtAdapter（新增）
```

统一接口（第一性原理：所有传统 MT 的差异收敛到 4 个能力）：

```ts
interface MtAdapter {
  id: string;
  /** 单次请求能携带的文本条数（腾讯 Batch 允许更多：实际可用 5-20，内部再分） */
  maxBatchSize: number;
  /** 单条文本长度上限（字节）；超长时适配器负责切分并重组 */
  maxItemBytes: number;
  /** 批量翻译：输入 N 条，按序返回 N 条（失败条目返回空串/错误文案） */
  translateBatch(texts: string[], cfg: MtRuntime, signal?: AbortSignal): Promise<string[]>;
  /** 最小连通性测试：返回一段可见的译文文本 */
  testConnection(cfg: MtRuntime, signal?: AbortSignal): Promise<string>;
}

interface MtRuntime {
  apiKey: string;      // DeepL Key；腾讯 SecretId
  apiSecret?: string;  // 腾讯 SecretKey（DeepL 无）
  endpoint: string;
  region?: string;     // 腾讯 Region（DeepL 无）
  targetLanguage: string; // 插件的展示语言（由适配器映射为自己语言的码）
}
```

### 3.3 配置模型：凭据形态泛化

现状 `ProviderSettings` 只有单密钥 `apiKey`；DeepL 恰好也是单密钥，掩盖了差异。
腾讯是 **SecretId + SecretKey 双密钥**（消息里 Key 口径：TC3 用 SecretId 参与签名、SecretKey 派生签名材料）。

第一性原理：**凭据是多字段的、随服务商而异的**，配置模型要允许 1~2 个密钥字段，
但 UI 与存储层对未使用的字段保持无视（sanitize 放行但不清零其他服务商字段）。

```ts
interface ProviderSettings {
  apiKey: string;      // LLM Bearer Key / DeepL Key / 腾讯 SecretId
  apiSecret?: string;  // 腾讯 SecretKey（新增，可选）
  endpoint?: string;
  model?: string;      // kind==='mt' 时不使用
  region?: string;     // 腾讯 Region（新增，可选，默认 ap-guangzhou）
  name?: string;       // 自定义服务商显示名（存量）
}
```

Options 页按 `kind` 渲染：
- `kind==='openai'`：现有 apiKey + endpoint + model（不变）
- `kind==='mt'`：apiKey(SecretId) + apiSecret(SecretKey) + endpoint + `region`（腾讯专属行，DeepL 隐藏）

## 四、腾讯适配器内部设计（service/tencent.ts）

### 4.1 TC3-HMAC-SHA256 签名器（核心复杂度）

```
CanonicalRequest =
  "POST" + "\n" +
  "/"      + "\n" +            // CanonicalURI（无 path）
  ""       + "\n" +            // CanonicalQueryString（POST+JSON，为空）
  "content-type:application/json; charset=utf-8\nhost:tmt.tencentcloudapi.com\n" + "\n" +
  "content-type;host" + "\n" +
  sha256hex(payload)
StringToSign =
  "TC3-HMAC-SHA256\n" + timestamp + "\n" +
  "2018-03-21/tmt/tc3_request\n" +
  sha256hex(CanonicalRequest)
SecretDate    = HMAC-SHA256("TC3" + SecretKey, utcDate)
SecretService = HMAC-SHA256(SecretDate, "tmt")
SecretSigning = HMAC-SHA256(SecretService, "tc3_request")
Signature     = hex(HMAC-SHA256(SecretSigning, StringToSign))
```

请求头：
`X-TC-Action: TextTranslateBatch`、`X-TC-Version: 2018-03-21`、`X-TC-Timestamp`、
`X-TC-Region: <ap-guangzhou>`、`Authorization: TC3-HMAC-SHA256 Credential=<SecretId>/<utcDate>/tmt/tc3_request, SignedHeaders=content-type;host, Signature=<sig>`、
`Content-Type: application/json; charset=utf-8`、`Host: tmt.tencentcloudapi.com`。

要点/坑：
- `host` 必须与请求的目标 host 完全一致（**用户若自定义 endpoint，host 用解析后的真实域名**，不能写死）；
- 签名里的 `utcDate` 是 UTC 日期 `YYYY-MM-DD`，`timestamp` 是秒级 Unix 时间戳，两者需同源取时，避免跨日边界不一致；
- 时间戳/签名只对单次请求有效，测试连接与真实请求分别签名；
- Node 无 `crypto.subtle` 异步问题——background 是 service worker，`crypto.subtle` 可用；但油猴 localBackground 的 shim 环境里 `crypto` 存在性需探测（`globalThis.crypto?.subtle` 缺失时降级）。
  更稳的写法：用同步 HMAC 实现（自写 30 行 HMAC-SHA256 或引入 tiny 依赖），双端行为一致、可单测。**推荐自写同步 HMAC**，与项目「零依赖、可单测」的风格一致。

### 4.2 语言映射（对齐 DeepL 的 `deeplTargetLang` 模式）

| 插件展示语言 | DeepL 码 | 腾讯码 |
|---|---|---|
| 简体中文 | ZH | `zh` |
| 繁體中文 | ZH-HANT | `zh-TW`（待核实） |
| English | EN | `en` |
| 日本語 | JA | `ja` |
| 한국어 | KO | `ko` |

Source 固定 `auto`（行内文本自动检测）；映射未知时回退 `zh`。
语言码常量表与 `deeplTargetLang` 同构，放 `tencent.ts` 顶部，测试覆盖全表。

### 4.3 批量与长度策略

内容侧候选段落上限 8,000 字符（`extractText` 的 `maxCharacters`），
而腾讯单条约 2,000 字节——**候选段落必然超限**。策略：

1. 适配器收到 5 条（现有 batchSize）后，按 `maxItemBytes` 把超长条目切成 ≤1,800 字符的块（留余量给多字节 UTF-8）；
2. 全部块拼成一个 TextTranslateBatch 请求（≤200 上限内）；
3. 返回后**按「一个段落的所有块」重组**为该段落的译文（块间以换行连接，段落级 1:1 契约不破坏，渲染器无感知）；
4. 空文本条目直接置空串，不进入请求（DeepL 对空文本抛 400，腾讯同理需先过滤）。

QPS 控制：现有 `BatchingScheduler` 并发 3、批 5 已天然限流（≈3 请求在途）；
适配器内对 `RequestLimitExceeded` 做 2 次简单退避重试（如 1s / 3s），其余错误直接归一化返回。

### 4.4 错误归一化

腾讯错误在 HTTP 200 的响应体 `Error.Code / Error.Message` 里（鉴权失败也可能是 HTTP 4xx）。
统一收敛成 `TranslationServiceError`，并给用户可操作文案（对齐 `common.ts` 的 429 处理风格）：

| Error.Code 前缀 | 用户文案 |
|---|---|
| `AuthFailure.*` / `Signature.*` | 「腾讯翻译鉴权失败：SecretId/SecretKey 可能有误或已过期，请检查设置。」+ 原始 Message |
| `RequestLimitExceeded.*` | 「腾讯翻译请求过于频繁（限流），已自动重试仍失败，请稍后再试。」 |
| `FailedOperation.*` / `InvalidParameter.*` | 「腾讯翻译请求被拒绝（参数或额度问题）：」+ 原始 Message |
| 其他 / HTTP 非 2xx | 通用「腾讯翻译服务请求失败 (status)：detail」，复用 `throwHttpError` 风格 |

### 4.5 连通性测试

复用 `testDeeplConnection` 模式：`TextTranslate` 单条 `hi`（Source=auto, Target=zh），
返回译文字符串即为通。Options 的「测试连接」按钮把 `kind:'mt'` 与 `providerId` 传出。

## 六、坑位清单（实现前必读）

1. **双密钥别混**：SecretId 在 `Authorization` 的 Credential 里明文出现，SecretKey 只进 HMAC，绝不能出现在任何请求体/URL/日志中（`logger.ts` 已按 `apiKey` 等键名脱敏，需确认 `apiSecret` 也被脱敏）。
2. **时间戳跨日**：`X-TC-Timestamp` 与签名 Date 必须同一时刻取值；跨 UTC 日边界重签，不要缓存签名。
3. **host 动态化**：用户自填 endpoint 时（内网网关/中转），签名与请求 host 必须一致，不能用内置常量。
4. **字符计费**：别把「已翻译段落」重复送译——段落级缓存（translationCache）是省钱的根，别在 MT 分支绕开它。
5. **QPS 默认 5**：并发与批次在 MT 分支收紧（现有 3 并发够用），重试只对限流码做、幂等安全。
6. **免费额度是账号维度**：500 万字符/月是腾讯侧给的，插件只负责提示不负责记账；P2 的用量统计只能近似。
7. **长段落重组**：切块重组的实现必须保持段落数 1:1（渲染层的 generation/顺序契约依赖它），测试里用「超长段落+正常段落混合」断言索引不错位。

## 七、为什么这样设计（一句话）

> 腾讯翻译不是第四个服务商，而是第二个「传统 MT 角色」——先立角色抽象（kind=`mt` + 适配器接口），
> 再落地腾讯适配器，DeepL 顺势迁移为新接口的存量实现；配置、UI、消息协议、油猴端全部零侵入或最小侵入。

## 附：微软翻译接入要点（方案 B，Edge 免密钥端点）

在第一性原理上，微软翻译与腾讯翻译**是同一角色**（传统 MT 网络 API：无模型、无提示词、无流式），
因此走同一套 `kind='mt'` 适配器机制，而非新的后端类型。差异化仅在三点：

| 差异点 | 处理 |
|---|---|
| 无鉴权 | 适配器不校验 apiKey；`isProviderConfigured` 对 `microsoft` 恒返回 true（免密钥即用）；后台 test-connection 对 microsoft 放行空 Key |
| 批量协议 | `POST https://edge.microsoft.com/translate/translatetext?from=&to=<code>&isEnterpriseClient=false`，body 为**裸 JSON 字符串数组**（非 `[{Text}]`），响应按序为 `[{translations:[{text}]}]`；`from` 空串 = 源语言自动检测 |
| HTML 对齐器 | 端点会对每个请求运行 HTML 标签对齐器，裸 `<` 会被融合为伪标签——发送前转义 `&`→`&amp;`、`<`→`&lt;`，接收后解码一次还原 |

工程要点与风险：

1. **方法来源**：该端点实现在开源项目 read-frog（GPLv3）中有同款适配器（2026-07 因微软下线旧令牌端点而迁移到当前 translatetext 直连）。本项目为思路层面的独立重写，文件头已注明来源。
2. **极其重要：该端点未公开、无 SLA**，随时可能像 2026-07 那样变协议。适配器集中在一个文件（`service/microsoft.ts`）、协议细节全部是模块顶部常量（URL / 语言码 / 转义），真机验证与后续维护都集中在单点。
3. 语言码：简体 `zh`（read-frog 验证过）；**繁中 `zh-TW` 待真机实测**（可能需 `zh-Hant`，届时改 `microsoftTargetLang` 一处即可）。
4. 超长段落：复用家族切块/重组（5000 字节阈值），批量 1:1 契约与腾讯一致。
5. UI：设置页与油猴面板对微软翻译隐藏「接口地址 / API Key / 模型」全部凭据字段，只留说明与「测试连接」。

## 附二：谷歌翻译接入要点（方案 C，translate-pa 免密钥端点）

与微软翻译同属"免密钥传统 MT"角色，复用同一套 `isNoKeyMtProviderId` 免密判定（微软 + 谷歌）。

| 项 | 内容 |
|---|---|
| 端点 | `https://translate-pa.googleapis.com/v1/translateHtml`（Google Workspace Translator 内部端点） |
| 鉴权 | 复用 Google 自家产品公共 key（`X-Goog-API-Key`，硬编码常量，非用户密钥）+ `client=wt_lib` |
| 请求体 | protobuf 风格嵌套数组 `[[[escapedText], fromLang, toLang], "wt_lib"]`，`Content-Type: application/json+protobuf`；`from=auto` 自动检测源语言 |
| 响应 | `result[0][0]` 为译文 HTML 字符串，客户端 HTML 解码一次还原 |
| HTML 转义 | 端点把请求文本当 HTML 解析，发送前转义 `& < > " '`，接收后解码（与微软适配器同构） |
| 批量 | v1 单文本/请求串行（与 read-frog 一致，最稳）；多文本批量化为后续优化 |
| 方法来源 | 开源项目 read-frog 的 google 适配器（GPLv3，思路学习 + 独立重写），文件头已注明 |

风险与约束（决策前必读）：

1. **国内可达性是最大现实约束**：端点在 `translate-pa.googleapis.com`，国内被墙，**国内用户大概率不可用**——这是比技术更重要的前置条件。
2. **未公开、无 SLA、ToS 灰色**：公共 key 可能被 Google 吊销（吊销即断，与微软 edge 端点同款风险）。
3. **Google 反滥用**：高频请求可能触发 429 / 封 IP。
4. 适配器集中单文件（`service/google.ts`），端点/key/client/语言码全部是顶部常量，真机验证与后续维护都在单点。
