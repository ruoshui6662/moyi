# 墨译油猴脚本 — 第一性原理迁移规划

> 目标：把「墨译」Chrome MV3 扩展移植为单文件用户脚本（UserScript），适配 Windows 桌面浏览器
> （Tampermonkey / Violentmonkey）与 Android 的 Via 浏览器，**保留现有功能逻辑**。

## 一、第一性原理：插件的本质是什么

剥掉形态，翻译插件只有一条管线和三样支撑物：

```
触发入口 → 页面文本采集 → 批量/流式调用翻译后端 → 双语渲染回填 DOM → 缓存/还原/状态管理
```

浏览器扩展形态提供的三样支撑物：

| 扩展能力 | 本质作用 | 油猴环境对应物 |
|---|---|---|
| background service worker | 代发跨域网络请求（页面 fetch 受 CORS 限制） | `GM_xmlhttpRequest`（跨域豁免） |
| `chrome.storage.local` | 配置/缓存持久化（跨站点共享、扩展私有） | `GM_getValue / GM_setValue`（+ 值变更监听） |
| popup / options / contextMenus / commands | 触发入口 + 设置 UI 宿主 | 页内自绘面板（closed shadow DOM）+ 悬浮按钮 + 页内快捷键 + `GM_registerMenuCommand` |

**关键洞察：油猴脚本 = content script 与 background 合体运行在同一闭包里。**
扩展中跨越进程边界的消息（`runtime.sendMessage` / `connect Port`），在脚本里退化为同一闭包内的函数调用。
因此迁移的第一性做法不是重写管线，而是**把消息总线本地化**：

1. 提供一个 `chrome.runtime` 最小 shim（sendMessage / onMessage / connect Port），在闭包内直连；
2. 用一个「本地 background」模块复刻 `background.ts` 的消息处理角色（直调 service 层）；
3. content 侧模块（trans / renderer / state / cache / floatingButton / main）**一行不改**，原样打包。

## 二、目标环境与约束

- **Tampermonkey（Windows Chrome/Edge）**：完整 GM_* API；`GM_xmlhttpRequest` 支持 `onprogress`
  增量 `responseText` → 可实现 SSE 流式渲染。
- **Via（Android）**：内置脚本引擎，支持常用 GM API（存储、xmlhttpRequest、菜单等）；流式能力不确定。
- 共同点：无后台进程、无 chrome.* API、页面 CSP 对 DOM 注入的 <style> 一般不拦、脚本沙箱内的全局污染不影响页面。

## 三、关键决策

### D1 网络层：GM_xmlhttpRequest 伪装成 fetch
service 层（common.ts / deepl.ts）直接调用全局 `fetch`。在脚本沙箱内把 `fetch` 替换为
GM_xmlhttpRequest 适配器（仅影响脚本作用域，页面不受污染），则 service 层零改动：
- 返回 Response-like 对象（ok/status/text()/json()/headers.get()）；
- AbortSignal 手动桥接（signal.addEventListener('abort') → gmRequest.abort()）；
- 校验端点 URL 的安全规则（公网强制 https、内网放行 http）原样保留。

### D2 流式渲染：单请求内自动降级
扩展的流式路径依赖 `response.body.getReader()`，GM 无法提供 ReadableStream。
方案：油猴侧不复用该传输函数，而是复用已导出的解析核心 `createTagStreamParser` +
提示词构造 `buildBatchMessages`，用 GM 的 `onprogress` 增量喂解析器：
- 有增量 → 逐段 partial/paragraph 渲染（真流式）；
- 无增量（Via 等不支持时）→ onload 后对完整文本走 `parseResponseBody` +
  标签提取，一次性出全部段落——**降级发生在同一个请求内部，无需预判能力**，
  渲染结果与非流式完全一致。

### D3 存储层：chrome.storage.local shim
现有模块只用了 `chrome.storage.local.get/set/remove/onChanged`。用 GM 存储实现这四个成员：
- Promise 化 get/set/remove；
- onChanged 由 `GM_addValueChangeListener`（remote 变更）驱动，实现多标签配置热同步；
- 无监听 API 时静默降级（每次翻译前本就会重新读配置）。
悬浮按钮位置、译文缓存沿用原有独立键名，与扩展版数据结构完全兼容。

### D4 入口收敛
扩展的四个入口（popup、右键菜单、chrome.commands、悬浮按钮）在脚本环境收敛为三个：
- **悬浮按钮**：点击翻译/还原（主入口，移动端可用）；**长按打开设置**；
- **页内快捷键**：录制机制照旧（keydown + isTrusted 校验 + 防抖）；
- **GM_registerMenuCommand**：翻译当前页 / 还原 / 打开设置（桌面管理器支持时注册）。

### D5 设置面板：页内 closed shadow DOM
复刻 options 页的全部能力：服务商管理（内置 5 家 + 自定义增删、获取模型、测试连接、关闭推理、
DeepL 套餐）、目标语言、提示词风格与自定义提示词、译文样式六件套 + 实时预览、快捷键录制、
清空缓存与恢复出厂。样式隔离在 shadow DOM 内，z-index 与扩展一致（2147483000）。

### D6 构建与产物
- esbuild 打包 IIFE 单文件，头部注入 UserScript 元数据（@match http/https、@noframes 对齐
  扩展仅顶层帧注入的行为、@connect * 允许自定义服务商任意域名）；
- 直接 import `src/**` 模块——**单一事实来源**，共享逻辑零复制，现有 vitest 测试继续守护；
- 仅两处纯增量改动允许落在共享代码上：导出 `extractStreamDelta`、`extractTaggedTranslations`
  （不改任何既有行为，扩展构建不受影响）。

## 四、目录结构

```
userscript/
  build.mjs             # esbuild 打包 + 元数据头拼接 => ../dist-userscript/moyi.user.js
  src/
    entry.ts            # 安装 shims → 注册本地 background → 动态 import 并启动 content main
    compat/gm.ts        # GM API 能力检测与最小类型声明
    compat/storageShim.ts   # chrome.storage.local → GM 存储
    compat/busShim.ts       # chrome.runtime 消息总线（sendMessage/onMessage/connect）
    compat/fetchShim.ts     # GM_xmlhttpRequest → fetch 兼容层
    localBackground.ts  # 复刻 background.ts 角色：translate/translate-batch/test-connection/
                        # fetch-models 处理器 + 流式端口处理
    settingsPanel.ts    # 页内设置面板（含长按入口）
package.json 新增 "build:userscript" 脚本
```

## 六、风险与对策

1. **CORS 类失败**（直接 fetch 中转站被拦）→ 已由 GM_xmlhttpRequest 根除；若某管理器连 GM_xhr 都没有，
   在 fetch shim 里回退原生 fetch 并给出可读错误。
2. **流式不可用** → 请求内自动降级（D2），无需用户感知。
3. **GM 存储异常**（隐私模式配额）→ 全部 try/catch 静默降级，不影响单次翻译。
4. **共享代码回归** → 除两处纯 export 外零改动；`npm run compile && npm test` 守护。
5. **Via 特殊性** → 所有 GM 能力经 typeof 探测后使用，缺失即降级，不假设、不硬崩。
